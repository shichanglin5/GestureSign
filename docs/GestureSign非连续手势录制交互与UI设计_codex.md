# GestureSign 非连续手势录制交互与 UI 设计

## 1. 设计目标

本设计用于统一 GestureSign 中**非连续手势**的创建、识别与展示方式。

这里的非连续手势包括：

- 轨迹手势
- 多指轻点（Tap）
- TipTap
- 后续的其他接触时序手势

设计目标：

- 保持与 GestureSign 现有“点击 `+` 后录制手势”的交互一致；
- 不让用户先理解复杂的手势分类概念；
- 由系统在录制完成后自动判断手势类型；
- 在动作列表中用清晰标签展示识别结果；
- 让连续手势继续保留独立配置面板，不混入录制型手势创建流程。

---

## 2. 总体交互原则

GestureSign 的手势交互分为两类：

## 2.1 连续手势

连续手势继续采用当前方式：

- 在独立栏目中点击 `+`
- 直接进入配置流程
- 不通过录制创建

原因：

- 连续手势是持续触发的；
- 用户需要配置滚动、缩放、连续方向等行为；
- 其本质不是“录制一个样本然后保存”。

## 2.2 非连续手势

非连续手势统一采用当前已有交互：

- 点击普通手势区的 `+`
- 打开录制面板
- 用户实际做出一个手势
- GestureSign 自动分析该手势属于哪一类
- 自动生成对应类型的配置

这样用户不需要先决定：

- 这是轨迹手势
- 还是轻点手势
- 还是 TipTap

系统负责在录制后自动识别。

---

## 3. 录制后处理流程

建议将非连续手势的录制后流程标准化为：

```text
用户录制手势
  -> 生成 RecordedGestureSample
  -> GestureAnalyzer 提取结构特征
  -> GestureClassifier 判断手势类别
  -> 生成具体配置对象
  -> 展示识别结果供用户确认
  -> 保存到应用配置
```

## 3.1 RecordedGestureSample

录制完成后，系统首先得到一份完整样本，至少包括：

- 全量 contact 轨迹
- contact id 生命周期
- finger count
- duration
- down/up 时序关系
- analysis 结果

## 3.2 GestureClassifier

分类器负责把录制样本分成：

- 轨迹手势
- 多指轻点
- TipTap
- 未来其他接触时序手势

## 3.3 生成配置对象

根据分类结果，生成对应配置：

- `TrajectoryGesture`
- `TapGestureConfig`
- `TipTapGestureConfig`

也就是说：

- 创建入口统一
- 内部存储模型分型

---

## 4. 用户录制完成后的反馈

录制完成后，不建议直接静默保存，而应显示一个轻量确认结果。

## 4.1 推荐交互

录制完成后，在录制面板中显示：

- 识别结果标题
- 手势示意图
- 主要标签
- `确认`
- `重录`

例如：

- `识别结果：3 指轻点`
- `识别结果：TipTap Left`
- `识别结果：4 指轨迹手势`

## 4.2 为什么需要确认

虽然 GestureSign 可以自动分类，但分类总会有边界场景。

增加一个轻量确认步骤，可以避免：

- 系统分类错误直接落配置
- 用户不知道系统识别成了什么

第一版建议：

- 只提供 `确认`
- `重录`

不强制提供“手动改类型”，避免交互过重。

---

## 5. 动作列表中的展示方式

GestureSign 现有动作列表建议继续保留，但对非连续手势条目增加“类型标签”展示。

## 5.1 轨迹手势

展示方式：

- 主标题：手势名称
- 标签：`轨迹`
- 标签：`N 指`
- 手势图：显示所有手指轨迹，而不是只显示特征手指

例如：

```text
自定义手势
[轨迹] [4 指]
```

## 5.2 多指轻点

展示方式：

- 主标题：`3 指轻点`
- 标签：`接触时序`
- 标签：`3 指`
- 示意图：简化点阵图，而不是复杂轨迹图

例如：

```text
3 指轻点
[接触时序] [3 指]
```

参数配置建议：

- 默认面板展示：`最大时长`、`最大位移`
- 默认不直接展示所有分析阈值，避免用户把 Tap 调成难以理解的阈值组合
- 若后续支持高指数组合优化，可在高级设置中显示“高指数组合抖动容忍”相关参数

## 5.3 TipTap

展示方式：

- 主标题：`TipTap Left`
- 标签：`接触时序`
- 标签：`1 fixed`
- 标签：`2 指`
- 示意图：fix fingers + tap finger 的语义化示意

例如：

```text
TipTap Left
[接触时序] [1 fixed] [2 指]
```

参数配置建议：

- 默认展示：
  - `固定指最小保持时长`
  - `tap 手指最大点击时长`
  - `固定指静止阈值`
  - `tap 手指最大位移`
  - `方向死区`
- `重复冷却时间` 建议放入高级设置

---

## 6. 手势图与示意图建议

## 6.1 轨迹手势

轨迹手势应显示：

- 全部手指轨迹
- 每根轨迹不同颜色或亮度
- 起点/终点可加箭头或圆点

不再只显示特征手指轨迹。

原因：

- 当前已经能获得完整多指数据；
- 只显示特征手指会误导用户；
- 多指语义手势需要完整视觉表达。

## 6.2 接触时序手势

接触时序手势不建议强行画完整轨迹，而应采用语义化示意：

### 多指轻点

- 显示若干点位
- 文本标注：`2 指轻点 / 3 指轻点 / 4 指轻点`

### TipTap

- fix fingers 用灰色点表示
- tap finger 用蓝色点表示
- 使用方向文字或简单箭头表示：
  - `Left`
  - `Middle`
  - `Right`

这样会比直接显示短促轨迹更清楚。

---

## 7. 控制面板结构建议

控制面板继续保留两个大区：

## 7.1 连续手势区

保持当前独立配置方式。

## 7.2 非连续手势区

保持当前动作列表交互，但每个录制生成的手势条目增加：

- 类型标签
- 指数标签
- fix fingers 标签（若适用）
- 更合理的图示策略

也就是说：

- 不新增一个复杂的新“ContactGesture 专区”来创建手势；
- 而是在现有普通动作创建交互之上增强识别与展示。

### 7.3 后续 UI 参数化要求

Tap / TipTap 当前已经在后端具备参数模型，但大部分阈值仍未进入 ControlPanel。

后续 UI 需要满足：

- 参数项直接映射到 `TapGestureRecognition` / `TipTapRecognition`，避免 UI 自己再维护一套识别语义。
- 训练与运行时使用同一组识别参数；训练模式只额外展示诊断信息，不允许 UI 引入“仅录制生效”的识别阈值。
- 高级参数需要有默认值说明，并支持一键恢复默认。
- 录制结果页后续可增加“当前识别参数”折叠区，便于定位边界样本为什么被分到 Tap / TipTap / Trajectory。

---

## 8. 与后端架构的对应关系

这个 UI 方案要求后端支持以下中间层：

## 8.1 录制样本对象

建议新增：

```csharp
class RecordedGestureSample
{
    public int FingerCount;
    public List<ContactFrame> Frames;
    public GestureAnalysis Analysis;
}
```

## 8.2 分类层

建议新增：

```csharp
RecordedGestureSample -> GestureClassifier -> ConcreteGestureConfig
```

也就是：

- UI 录制只负责拿样本
- 后端分类器负责决定类型
- 最终生成具体配置对象并保存

## 8.3 配置层

最终保存模型仍然应分开：

- `TrajectoryGestures`
- `ContinuousGestures`
- `ContactGestures`

UI 虽然统一入口，但存储层仍按手势类型分开。

---

## 9. 推荐的第一版实现范围

为了控制复杂度，第一版建议支持：

- 轨迹手势录制后正常保存
- 多指轻点自动识别并展示标签
- TipTap Left / Right / Middle 自动识别并展示标签
- 轨迹手势显示所有手指轨迹
- 接触时序手势显示简化语义图

第一版不建议做：

- 手动修改自动识别出的手势类型
- 太多高级阈值在主界面直接暴露
- 一次支持过多接触时序手势变体

---

## 10. 结论

在当前 GestureSign 的产品形态下，最合适的交互方式是：

- **连续手势继续单独配置**
- **非连续手势继续统一通过录制创建**
- **录制完成后由系统自动识别类型**
- **在动作列表中通过标签和语义图展示类型**
- **轨迹手势从“特征手指图”升级为“全手指轨迹图”**

一句话总结：

- 创建入口统一
- 内部模型分型
- 展示层按手势语义优化
