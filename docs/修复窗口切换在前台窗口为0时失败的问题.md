# 修复窗口切换在前台窗口为 0 时失败的问题

## 问题现象

在微信公众号页面（嵌入式 WebView）中使用触控板手势触发"切换窗口"操作时：
- 第一次手势无效，窗口没有切换
- 需要执行两次手势才能成功切换
- 日志显示 `ForegroundWindow=0x0`，且在 `Windows.Internal.Shell.TabProxyWindow` 和 `Windows 输入体验` 之间反复弹跳

## 根因分析

### 1. 触摸手势导致前台窗口瞬间丢失

这是 Windows 的已知行为。微软文档明确说明：

> "The foreground window can be NULL in certain circumstances, such as when a window is losing activation."
> — [GetForegroundWindow (winuser.h)](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getforegroundwindow)

触摸输入通过 WM_POINTER/WM_TOUCH 路径处理，会导致窗口激活状态短暂转换，期间 `GetForegroundWindow()` 返回 0。

### 2. IsSwitchableWindow 未过滤系统窗口

`EnumWindows` 枚举的窗口列表中包含了不应出现的系统窗口：
- `Windows.Internal.Shell.TabProxyWindow`（Explorer.exe 的任务栏标签代理窗口）
- `Windows 输入体验`（TextInputHost.exe，DWM Cloaked 的 UWP 系统应用）

这些窗口有标题、可见、无 owner、非 ToolWindow，通过了所有原有过滤条件。

### 3. ForceSetForegroundWindow 在前台为 0 时全面失效（核心问题）

`ForceSetForegroundWindow` 使用三层策略激活窗口，但在前台窗口为 0 时全部失效：

- **方法 1**：`SetForegroundWindow(hWnd)` — 调用进程不是前台进程，被 Windows 拒绝
- **方法 2**：`AttachThreadInput` — `GetWindowThreadProcessId(0, ...)` 返回无效线程 ID (0)，`AttachThreadInput` 失败；`keybd_event(0, 0, ...)` 模拟 VK code 为 0 的空按键，Windows 不将其视为有效用户输入
- **方法 3**：`SetWindowPos` + `SetForegroundWindow` — 只改变 Z-order，仍无前台权限

根据 [SetForegroundWindow 文档](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)，成功条件之一是 "the calling process received the last input event"。VK code 0 不满足此条件。

## 修复方案

### 修改 1：过滤系统窗口（NextApplication.cs IsSwitchableWindow）

添加两项过滤：

```csharp
// 过滤 DWM Cloaked 窗口（如 TextInputHost）
DwmGetWindowAttribute(hWnd, DWMWA_CLOAKED, out int cloaked, sizeof(int));
if (cloaked != 0) return false;

// 过滤 Shell 内部窗口（如任务栏代理窗口）
GetClassName(hWnd, className, capacity);
if (className == "Windows.Internal.Shell.TabProxyWindow") return false;
```

### 修改 2：前台窗口为 0 时的回退链（NextApplication.cs Gestured）

```
GetForegroundWindow() → ActionPoint.WindowHandle → CaptureWindow → windows[0]
```

当所有 API 都返回 0 时，使用 `EnumWindows` Z 序最顶层的窗口作为"当前窗口"，确保切换到下一个窗口而非当前窗口自身。

### 修改 3：使用 ForceSetForegroundWindow 替代 SetForegroundWindow（NextApplication.cs）

通过 `SystemWindow.ForegroundWindow` setter 调用 `ForceSetForegroundWindow`，使用多层策略确保窗口激活。

### 修改 4：修复 ForceSetForegroundWindow 在前台为 0 时的失效（SystemWindow.cs，核心修复）

两处关键修改：

1. **`keybd_event(0, 0, ...)` → `keybd_event(VK_MENU, 0, ...)`**

   使用 Alt 键（VK_MENU = 0x12）替代无效的 VK code 0。这是社区广泛验证的标准 workaround，让 Windows 认为调用进程收到了用户输入，从而获得 `SetForegroundWindow` 的调用权限。

   参考：[Problems with SetForegroundWindow Calls](https://www.damirscorner.com/blog/posts/20060603-ProblemsWithSetForegroundWindowCalls.html)

2. **`AttachThreadInput` 前置检查 `foregroundThreadId != 0`**

   当前台窗口为 0 时，`GetWindowThreadProcessId(0, ...)` 返回无效线程 ID，`AttachThreadInput` 必然失败。跳过无效的线程附加操作。
