# GestureSign 兼容说明文档

## 1. 目的

本文件用于记录当前 GestureSign 为了保证平滑迁移而保留的兼容逻辑，包括：

- 旧轨迹手势数据兼容
- 旧动作绑定兼容
- 旧连续手势配置兼容
- 旧 UI / 旧消息链路兼容边界

后续当项目确认“不再需要兼容旧逻辑”时，应以本文件为依据进行集中清理，避免遗漏影响运行时行为的旧分支。

---

## 2. 总体原则

当前兼容策略遵循以下原则：

1. **优先保证旧配置可继续读取和运行**
2. **新模型优先，新字段优先，旧字段作为回退**
3. **一旦用户重新保存配置，应尽量写回新模型**
4. **对于已经明确废弃的产品能力，只做最小兼容读取，不承诺保持原行为**

---

## 3. 旧轨迹手势兼容

## 3.1 旧手势缺失 `GestureId`

### 当前兼容方式

轨迹手势加载时：

- 若旧手势没有 `Id`
- 系统会自动生成一个稳定的 `GestureId`
- 若检测到重复 `GestureId`
  - 自动修复为新的唯一 id
  - 记录 warning 日志
  - 加载完成后回写保存

### 相关代码

- `GestureSign.Common/Gestures/GestureManager.cs`

### 未来可清理条件

满足以下条件后可删除“缺失 Id 自动补全”逻辑：

- 所有线上/用户配置中的轨迹手势都已带稳定 `GestureId`
- 启动日志长期不再出现 `Duplicate/empty gesture id repaired`

---

## 3.2 旧轨迹手势无 `DisplayPointPatterns`

### 当前兼容方式

- 若手势未包含 `DisplayPointPatterns`
- UI 展示回退到 `PointPatterns`

### 影响

- 旧手势仍可正常显示
- 但只有新录制的轨迹手势才可能显示“全手指轨迹”

### 相关代码

- `GestureSign.Common/Gestures/Gesture.cs`
- `GestureSign.ControlPanel/Converters/GestureImageConverter.cs`

### 未来可清理条件

满足以下条件后可删除 fallback：

- 所有手势定义都已包含 `DisplayPointPatterns`
- 不再存在旧格式轨迹手势文件

---

## 4. 旧动作绑定兼容

## 4.1 旧动作仅使用 `GestureName`

### 当前兼容方式

动作执行与显示时：

- 优先按 `GestureId` 查找手势定义
- 若没有 `GestureId`
  - 回退按 `GestureName`

### 相关代码

- `GestureSign.Common/Applications/ApplicationManager.cs`
- `GestureSign.Common/Plugins/PluginManager.cs`
- `GestureSign.ControlPanel/ViewModel/CommandInfo.cs`
- `GestureSign.ControlPanel/ViewModel/CommandInfoProvider.cs`
- `GestureSign.ControlPanel/Dialogs/ActionDialog.xaml.cs`

### 风险说明

- 只要仍保留按名称回退，就必须同时维护 `GestureName` 的可用性
- 修改已有手势名称时，需要同步更新所有绑定的 `GestureName`

### 未来可清理条件

满足以下条件后可删除 `GestureName` 回退：

- 所有 Action 都已带 `GestureId`
- 运行时已不再出现基于 `GestureName` 的绑定命中
- 控制面板与导入导出链路都已彻底迁移到 `GestureId`

---

## 5. ContactGesture 兼容

## 5.1 Tap / TipTap 当前状态

Tap / TipTap 是新增模型，不存在传统意义上的旧格式兼容问题。

但当前仍处于“新旧架构并存”的过渡阶段：

- 已具备全局定义对象：
  - `TapGestureConfig`
  - `TipTapGestureConfig`
- 动作层已支持通过 `GestureId` 绑定这类定义
- 控制面板录制后已能自动分类并创建定义对象

### 当前兼容边界

- 旧版本不会包含 `ContactGestures`
- 不需要做旧结构反序列化迁移
- 但录制链和动作绑定链仍保留与轨迹手势并行的兼容逻辑

---

## 6. 旧连续手势兼容

## 6.1 旧模型

旧连续手势使用：

- `ContinuousGestureSettings`
- `ContinuousGestureConfig`
- 支持 2/3/4 指
- 支持 `Custom` 模式和方向命令

## 6.2 当前兼容方式

当前产品方向已经收敛为：

- 两指滑动
- 两指缩放

但为了减少改动风险：

- 运行时仍通过适配层把 `TwoFingerGestureSettings` 映射成内部 `ContinuousGestureConfig`
- 某些旧连续手势数据结构仍存在于代码中作为兼容壳层

### 已废弃能力

以下能力已从产品和主流程中废弃：

- 3/4/5 指连续手势
- 连续方向命令
- `Custom` 连续模式

### 相关代码

- `GestureSign.Common/Applications/TwoFingerGestureSettings.cs`
- `GestureSign.Daemon/Triggers/ContinuousGestureTrigger.cs`
- `GestureSign.ControlPanel/MainWindowControls/AvailableActions.cs`
- `GestureSign.ControlPanel/Dialogs/ContinuousGestureConfigDialog.xaml.cs`

### 未来可清理条件

满足以下条件后，可彻底删除旧连续手势兼容壳层：

- 不再需要读取历史 `ContinuousGestureSettings/Config` 数据
- 控制面板和运行时全部只使用 `TwoFingerGestureSettings`
- `ContinuousGestureConfig` 不再被任何新路径依赖

---

## 7. 旧录制链兼容

## 7.1 `GotNewPattern` / stack-up 历史逻辑

旧控制面板录制链路主要依赖：

- `PointPattern[]`
- `GotNewPattern`
- stack-up 双击叠加录制

当前已基本切换到：

- `RecordedGestureDefinitionResult`
- `GotNewGestureDefinition`

### 当前状态

- `GotNewPattern` 主链已移除
- stack-up 旧逻辑不再作为主路径
- 录制主链已切换到自动分类结果对象

### 未来可清理条件

当确认没有任何 UI 或导入导出路径仍依赖旧 `PointPattern[]` 录制消息时，可彻底删除旧录制兼容概念与相关注释。

---

## 8. 全局手势定义与绑定的过渡状态

当前已经形成：

- 轨迹手势：稳定 `GestureId`
- Tap / TipTap：稳定 `Id`
- Action：支持 `GestureId + GestureName`

但还没有完全实现：

- 所有手势都由统一的“全局定义管理入口”维护
- 所有手势编辑都完全通过统一的“定义库 + 绑定层”完成

因此目前仍是一个**过渡态**：

- 架构方向已经明确
- 主链已经打通
- 部分管理入口与 UI 仍在逐步收敛

---

## 9. 后续清理建议顺序

建议将旧逻辑清理分三轮进行：

### 第一轮：删除显式废弃功能

- 旧连续方向命令相关结构
- 旧 `Custom` 连续模式残留
- 失效的旧录制路径和死代码

### 第二轮：删除兼容回退

- `GestureName` 回退绑定
- `DisplayPointPatterns -> PointPatterns` fallback
- 旧连续手势配置读取兼容

### 第三轮：统一定义管理

- 将轨迹 / Tap / TipTap 统一纳入真正的全局定义管理入口
- 让应用只保留绑定层
- 清理残留的“局部定义 + 全局定义并存”逻辑

---

## 10. 当前结论

当前项目仍然保留了一些兼容逻辑，但这些兼容逻辑都属于：

- 有明确保留理由
- 有明确未来可清理条件
- 已知范围可控

后续当项目确认：

- 所有数据都完成迁移
- 不再需要读取旧配置
- 所有 UI 和执行链都完全围绕新模型运行

即可按本文件的顺序逐步移除这些兼容逻辑。
