# 状态机全流程分析与优化方案

## 一、概念澄清

### CapturingInvalid 是什么状态

`CapturingInvalid` 是 `TryBeginCapture` 设置的初始捕获状态，含义是"手指已落在板上，但尚未产生有效移动"。它在 `AddPoint` 中当特征手指移动距离超过 `MinimumPointDistance` 阈值时转为 `Capturing`。

```
Ready → TryBeginCapture → CapturingInvalid → (移动超阈值) → Capturing
```

这个状态的设计意图是：区分"手指静止放在板上"和"手指已经开始画轨迹"。对于 Tap/Click 手势，手指不移动就不会从 `CapturingInvalid` 转为 `Capturing`。

### 只有 TipTap 有 Session 吗

不是。所有手势类型都通过 `CreateSessionSnapshot()` 创建 `GestureSessionSnapshot`（包含 ActiveContactIds、时间戳、PrimaryButton 等信息），用于识别器的判定。

TipTap 额外拥有一个 **独立的会话状态机**（`_tipTapSessionActive` 标志 + `_tipTapRecognizer.State`），因为 TipTap 需要在 fix 手指保持不动的情况下多次检测 tap cycle，不能用标准的 Capturing 状态机表示。

### CaptureState 枚举

```csharp
public enum CaptureState
{
    Ready,              // 空闲
    Disabled,           // 系统禁用（UI 弹出等）
    Capturing,          // 手指在移动，正在录制轨迹
    CapturingInvalid,   // 手指在板上但未有效移动
    TriggerFired        // 遗留状态，当前未被任何代码设置到 State
}
```

## 二、当前状态机全流程

### 2.1 PointDown 流程

```
PointDown
  ├─ TipTap session 活跃 → HandleTipTapPointDown（独立处理）
  │
  ├─ TrackAllPoints（维护 _activeContactIds、轨迹、timing）
  │
  ├─ 已在 Capturing/CapturingInvalid → 更新 _totalFingerCount，return
  │
  ├─ _pendingFirstPoints != null（delay 中）→ 合并新手指，尝试 TipTap promote
  │
  └─ Ready 状态
       ├─ MultiFingerDelay > 0 → 暂存 pending，启动 delay timer
       ├─ delay == 0 → 尝试 TipTap session
       └─ TipTap 不匹配 → TryBeginCapture → CapturingInvalid
```

### 2.2 PointMove 流程

```
PointMove
  ├─ TipTap session → HandleTipTapPointMove（追踪 tap 手指位移）
  │
  ├─ TrackAllPoints
  │
  ├─ _pendingFirstPoints != null（delay 中）
  │    ├─ 最大移动 ≥ TapDistanceThreshold → 取消 timer，StartCaptureAfterDelay
  │    └─ 移动不够 → 继续等待 delay
  │
  └─ Capturing/CapturingInvalid → AddPoint
       └─ 特征手指移动 ≥ MinimumPointDistance → CapturingInvalid → Capturing
```

### 2.3 PointUp 流程

```
PointUp
  ├─ TipTap session → HandleTipTapPointUp
  │    ├─ tap 手指释放 → 尝试匹配 TipTap → 成功则执行
  │    └─ 所有手指释放 → TryRecognizeTerminalContactGesture → fallback 到 trajectory
  │
  ├─ TrackAllPoints
  │
  ├─ Case 1: _pendingFirstPoints != null（delay 中）
  │    ├─ 不是所有手指释放 → return（等待）  ✅ 正确
  │    └─ 全部释放 → StartCaptureAfterDelay → EndCapture → 识别 tap/click
  │
  ├─ Case 2: Capturing 或 (CapturingInvalid && allReleased)
  │    └─ EndCapture()  ← ⚠️ Capturing 状态不检查 allContactsReleased
  │
  └─ TriggerFired → Ready
```

### 2.4 EndCapture 流程

```
EndCapture
  ├─ CreateSessionSnapshot（快照 ActiveContactIds、timing 等）
  ├─ GestureAnalyzer.Analyze（计算 IsTapLike、MaxPerFingerDistance 等）
  ├─ TryRecognizeContactGesture
  │    ├─ Click 识别器（需要 HasPrimaryButtonClick + 所有手指释放 + 短时长 + 小位移）
  │    └─ Tap 识别器（需要所有手指释放 + 短时长 + IsTapLike）
  │
  ├─ 训练模式 → GestureDefinitionFactory.Create → 发送给 ControlPanel
  │
  ├─ 运行时 → 按优先级匹配：
  │    1. Click → 执行
  │    2. Tap → 执行
  │    3. TipTap（终端识别）→ 执行
  │    4. 轨迹手势 → PointPatternAnalyzer 匹配
  │
  └─ State = Ready
```

### 2.5 连续手势流程

```
ContinuousGestureTrigger 订阅 PointCaptured 事件
  ├─ State 必须是 Capturing 或 CapturingInvalid
  ├─ fingerCount 必须 == 2
  ├─ 每帧检测滚动/缩放 → OnTriggerFired → 执行 action
  └─ CaptureEnded → 惯性滚动
```

连续手势**不改变 CaptureState**，寄生在标准的 Capturing 流程上。

## 三、问题分析

### 问题 1：Capturing 状态下 PointUp 不等待所有手指释放（P0 严重）

**位置**: PointCapture.cs:730

```csharp
// Case 2: Already capturing - keep legacy behavior for now
if (State == CaptureState.Capturing || (State == CaptureState.CapturingInvalid && allContactsReleased))
```

`Capturing` 状态下，**第一个手指 up 就触发 EndCapture**。此时 `_activeContactIds` 非空，Click/Tap 识别器直接 return false。

这是 4 指 Click/Tap 被误分类为 Trajectory 的直接原因。

**对比**：Case 1（pending 阶段）正确地等待 `allContactsReleased`。

### 问题 2：MultiFingerDelay 不再必要（P1 架构）

详见 [04_MultiFingerDelay不再必要的分析.md](04_MultiFingerDelay不再必要的分析.md)。

Hybrid 修复后每帧数据完整，delay 变为不必要的延迟和状态复杂度。所有手势类型在无 delay 时都能正确工作。

### 问题 3：_totalFingerCount 冗余（P1 架构）

详见 [05_totalFingerCount冗余分析.md](05_totalFingerCount冗余分析.md)。

`_totalFingerCount` 通过 `Math.Max` 在 5 个位置累积，与 `_activeContactIds.Count` 的信息重复。

### 问题 4：TipTap 进入路径混乱（P2 可维护性）

TipTap 有两个进入时机：
1. `PointDown` 中 `Ready` 状态 → `TryBeginTipTapSession`（delay == 0 时）
2. `MultiFingerDelayCallback` → `TryBeginTipTapSession`（delay 超时时）
3. `_pendingFirstPoints` 中新手指 down → `TryPromotePendingToTipTap`（delay 期间）

三条路径最终都进入同一个 TipTap 会话，但中间状态不同。去掉 delay 后可简化为：
- `PointDown` 的 `Ready` 状态 → `TryBeginTipTapSession`
- `CapturingInvalid` 中新手指 down → 如果满足条件则 promote 到 TipTap

### 问题 5：TriggerFired 状态是死代码（P3 清理）

`TriggerFired` 枚举值存在但没有任何代码将 `State` 设置为 `TriggerFired`。`PointUp` 中有处理它的分支（转为 Ready），但永远不会执行。

连续手势 Trigger 通过事件订阅工作，不使用 `CaptureState`。

### 问题 6：CapturingInvalid 中新手指 down 缺少 TipTap promote（P2 功能）

当前在 `CapturingInvalid` 中收到新手指 down 时，只更新 `_totalFingerCount`，**不尝试 TipTap promote**。这意味着：

场景：用户 2 指落下（进入 CapturingInvalid），第 3 指落下（应该进入 TipTap），但当前代码直接 return，不做 TipTap 检测。

有 delay 时，这个 case 由 `_pendingFirstPoints` 分支处理（合并后 promote）。去掉 delay 后，需要在 `CapturingInvalid` 的 already-capturing 分支增加 TipTap promote 检查。

### 问题 7：CapturingInvalid 中 PointUp 的条件不对称（P2）

```csharp
if (State == CaptureState.Capturing || (State == CaptureState.CapturingInvalid && allContactsReleased))
```

`CapturingInvalid` 的 PointUp **只有全部释放才进 EndCapture**，而 `Capturing` 的 PointUp **任意释放就进 EndCapture**。

这导致一个奇怪的不对称：
- 手指落下后静止不动（CapturingInvalid），手指逐个抬起 → 等全部释放后 EndCapture ✅
- 手指落下后移动了一点（Capturing），第一个手指抬起 → 立即 EndCapture ❌

修复后，两种状态都应该等待所有手指释放。

### 问题 8：pending 阶段 PointUp 的 `PreserveReleasedContactsForPendingTap` 逻辑（P3）

```csharp
// Case 1: pending 阶段 up，全部释放
StartCaptureAfterDelay();           // TryBeginCapture → _activeContactIds 初始化
PreserveReleasedContactsForPendingTap();  // 从 _activeContactIds 中移除已 up 的
EndCapture();
```

这段代码先 `StartCaptureAfterDelay`（初始化 `_activeContactIds`），再手动移除已释放的触点。这是因为 `TryBeginCapture` 把所有 pending 点（包括已 up 的）都算作 active。

去掉 pending 机制后，`TrackAllPoints` 实时维护 `_activeContactIds`，在全部释放时 `_activeContactIds` 本来就为空，不需要这个补丁。

## 四、各手势类型的完整分流路径（当前 vs 重构后）

### 轨迹手势（如 3 指滑动）

| 阶段 | 当前（有 delay） | 重构后（无 delay） |
|---|---|---|
| 手指 down | 暂存 pending | Ready → TryBeginCapture → CapturingInvalid |
| 静止等待 | delay timer 计时 | 停留在 CapturingInvalid |
| 手指开始移动 | move > threshold → StartCaptureAfterDelay → Capturing | AddPoint → CapturingInvalid → Capturing |
| 手指持续移动 | AddPoint | AddPoint |
| 手指释放 | EndCapture（⚠️ 第一个手指 up 就结束）| 等全部释放 → EndCapture |
| 识别 | PointPatternAnalyzer | PointPatternAnalyzer（行为不变） |

### Tap 手势（如 4 指 tap）

| 阶段 | 当前（有 delay） | 重构后（无 delay） |
|---|---|---|
| 手指 down | 暂存 pending | Ready → TryBeginCapture → CapturingInvalid |
| 手指不移动 | pending 中不产生 move | CapturingInvalid 中 AddPoint 不超阈值 → 保持 |
| 手指全部释放 | Case 1: StartCapture → EndCapture | PointUp → allReleased → EndCapture |
| 识别条件 | IsTapLike + 全部释放 + duration ≤ MaxDurationMs | 相同（行为等价） |

### Click 手势（如 3 指 click）

| 阶段 | 当前 | 重构后 |
|---|---|---|
| 手指 down + 按下物理按键 | 暂存 pending | CapturingInvalid |
| 手指释放 + 松开按键 | Case 1: StartCapture → EndCapture | PointUp → allReleased → EndCapture |
| 识别条件 | HasPrimaryButtonClick + 全部释放 + duration + 小位移 | 相同 |

### TipTap 手势（如 2 指 fix + 1 指 tap）

| 阶段 | 当前（有 delay） | 重构后（无 delay） |
|---|---|---|
| fix 手指 down | 暂存 pending | Ready → TryBeginTipTapSession（如果有匹配的 TipTap 配置） |
| delay 超时/新手指 down | TryBeginTipTapSession / TryPromote | 已在 TipTap session |
| tap 手指 down | HandleTipTapPointDown（设置 tapFingerId） | 相同 |
| tap 手指 up | TryRecognizeTipTapFromCurrentSession | 相同 |
| 全部释放 | TryRecognizeTerminalContactGesture → fallback trajectory | 相同 |

**注意**：如果没有匹配的 TipTap 配置，`TryBeginTipTapSession` return false，接着走普通 `TryBeginCapture` 路径。

### 连续手势（如 2 指滚动/缩放）

| 阶段 | 当前 | 重构后 |
|---|---|---|
| 手指 down | pending / TryBeginCapture | TryBeginCapture → CapturingInvalid |
| 手指移动 | CapturingInvalid → Capturing | 相同 |
| 连续帧 | ContinuousGestureTrigger 通过 PointCaptured 事件检测 | 相同（不受影响） |
| 手指释放 | EndCapture → 惯性滚动 | 等全部释放 → EndCapture → 惯性滚动 |

连续手势不受本次重构影响——它订阅 `PointCaptured` 事件，不依赖 pending/delay 机制。

## 五、边缘 Case 分析

### Edge 1: 手指不同时落下（16ms 间隔）

4 指 tap 时手指间隔约 16ms 逐个落下。

- **重构后**：第一个手指 down → CapturingInvalid（`_peakFingerCount=1`），后续手指 down → `_peakFingerCount` 更新到 2、3、4。全部释放后 EndCapture，FingerCount = 4。✅

### Edge 2: 手指不同时抬起（16ms 间隔）

4 指 tap 释放时手指间隔约 16ms。

- **当前 bug**：Capturing 状态下第一个手指 up 就 EndCapture，ActiveContactIds 非空
- **重构后**：等全部释放后 EndCapture，ActiveContactIds 为空。✅

### Edge 3: 轨迹手势中途部分手指抬起

3 指滑动时，1 指先抬起，其余 2 指继续滑动。

- **重构后**：1 指 up → `_activeContactIds.Count = 2`，不是全部释放 → 不 EndCapture → 继续 Capturing → 2 指都 up → EndCapture。FingerCount = 3（`_peakFingerCount` 记录最大值）。✅ 对轨迹手势无影响。

### Edge 4: SurfaceForm 画线闪烁

去掉 delay 后，tap/click 手势也走 `TryBeginCapture` → `CaptureStarted` → `StartDrawing`。

- **分析**：`StartDrawing` 只做初始化（清除画布、设置画笔），**不调用 `Show()`**。窗口的 `Show()` 在 `DrawSegments` 中，而 `DrawSegments` 只在 `DrawPoints` 收到有效移动点时才调用。tap/click 手指不移动 → `AddPoint` 中距离 < `MinimumPointDistance` → 不触发 `PointCaptured` 事件 → `DrawPoints` 不被调用 → **窗口从未显示**。
- 快速连续 tap 时，只有 `StartDrawing` 的轻量初始化成本，不会有窗口闪烁。✅

### Edge 5: TipTap 进入——fix 手指在 CapturingInvalid 中

2 指落下进入 CapturingInvalid，第 3 指 down 应进入 TipTap。

- **当前**：由 pending 阶段的 `TryPromotePendingToTipTap` 处理
- **重构后**：需要在 already-capturing 分支（CapturingInvalid）检测 TipTap promote。如果 `TryBeginTipTapSession` 匹配，则从 CapturingInvalid 转入 TipTap session。
- **实现**：在 `if (State == CaptureState.CapturingInvalid)` 分支中，新手指 down 时尝试 promote。✅ 需要注意从 CapturingInvalid 切换到 TipTap 时，要重置 CapturingInvalid 的状态。

### Edge 6: 快速连续手势——前一个手势的手指未完全释放就开始下一个

- **重构后**：前一个手势等全部释放后 EndCapture → State=Ready → 下一个手指 down 是全新的 session。不会有重叠。✅

### Edge 7: 惯性滚动与 EndCapture 的时序

等全部释放后才 EndCapture，意味着 `CaptureEnded` 事件（触发惯性滚动）的时机延后约 16ms。

- **分析**：惯性滚动需要最后一帧的速度。延后 16ms 不影响速度计算（最后移动帧的速度已经被 `_velocityHistory` 缓存）。但需确认 `_velocityStopwatch.ElapsedMilliseconds` 不会因延后导致超过 80ms 阈值。
- **风险**：如果手指抬起后 80ms 内才收到最后的 up 事件（极端情况），可能跳过惯性。实际硬件报告频率约 8ms/帧，4 指逐个释放约 48ms，仍在 80ms 窗口内。✅

### Edge 8: 训练模式下 1 指被过滤

```csharp
if (Mode == CaptureMode.Training && totalFingerCount < 2)
    return false;
```

去掉 delay 后，`totalFingerCount` 是第一个 PointDown 事件的值（可能只有 1 指），`TryBeginCapture` 会 return false。后续手指 down 时 State 仍为 Ready，会再次尝试 TryBeginCapture。

- **用 `_peakFingerCount` 后**：第一个 down 时 `_activeContactIds.Count = 1`，TryBeginCapture 被拒。第二个 down 时 `_activeContactIds.Count = 2`，TryBeginCapture 通过。但此时第一个手指的初始位置没有被 `TryBeginCapture` 的 `firstPoint` 包含。
- **解决**：TryBeginCapture 改为用 `_activeContactIds` 相关数据（而非 `e.InputPointList`），或在 Ready 状态下总是先 TryBeginCapture（即使 1 指），训练模式的过滤移到 EndCapture 阶段。
- **推荐**：保持当前行为——训练模式需要 2 指以上才开始捕获，第一个手指 down 被跳过。第二个手指 down 时 `e.InputPointList` 包含第二个手指，第一个手指的轨迹已在 `_allPointsCaptured` 中通过 `TrackAllPoints` 记录。`TryBeginCapture` 的 `firstPoint` 用于初始化 `_pointsCaptured`（特征手指轨迹）和 `_featureFingerIds`。关键是确保 `_allPointsCaptured` 不被重复初始化丢失数据——当前代码在 `TryBeginCapture` 中 `_allPointsCaptured = new`，会丢失第一个手指的轨迹。
- **修复**：改为 `_allPointsCaptured ??= new`，或在 TrackAllPoints 中已经维护好 `_allPointsCaptured`，TryBeginCapture 不要重新 new。

## 六、重构后的新状态机

```
Ready
  │
  ├─ finger down
  │    ├─ TryBeginTipTapSession 匹配 → TipTap session（独立状态机）
  │    └─ TryBeginCapture → CapturingInvalid
  │
  ├─ CapturingInvalid
  │    ├─ finger down
  │    │    ├─ 更新 _peakFingerCount
  │    │    └─ 尝试 TipTap promote（如果有匹配的 TipTap 配置）
  │    ├─ move → AddPoint
  │    │    └─ 特征手指移动 ≥ MinimumPointDistance → Capturing
  │    ├─ up（全部释放）→ EndCapture（判定 tap/click/trajectory）
  │    └─ up（部分释放）→ 等待
  │
  ├─ Capturing
  │    ├─ finger down → 更新 _peakFingerCount
  │    ├─ move → AddPoint + PointCaptured 事件（连续手势在此订阅）
  │    ├─ up（全部释放）→ EndCapture（判定 trajectory / 连续手势惯性）
  │    └─ up（部分释放）→ 等待
  │
  └─ TipTap session（独立状态机）
       ├─ fix 手指保持 + tap 手指 down/up → 匹配 TipTap cycle
       ├─ 全部释放 → TryRecognizeTerminalContactGesture → fallback trajectory
       └─ 失败 → ResetSessionTracking
```

**移除的元素**：
- `_pendingFirstPoints` / `_pendingTotalFingerCount` / `_pendingStartedAt`
- `_multiFingerDelayTimer` / `MultiFingerDelayCallback`
- `StartCaptureAfterDelay()` / `PreserveReleasedContactsForPendingTap()`
- `TriggerFired` 枚举值（死代码）
- `_totalFingerCount` → 改为 `_peakFingerCount`（在 TrackAllPoints 中自动追踪）
- `e.TotalFingerCount` / `_pendingTotalFingerCount` 的依赖

**新增的元素**：
- `_peakFingerCount`：在 TrackAllPoints 中 `Math.Max(_peakFingerCount, _activeContactIds.Count)` 追踪
- CapturingInvalid 中新手指 down 时的 TipTap promote 检查
