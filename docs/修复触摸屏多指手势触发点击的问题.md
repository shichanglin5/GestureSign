# 修复触摸屏多指手势结束时触发点击的问题

## 问题描述

在抖音（Edge 浏览器）中，通过触摸屏执行多指手势（双指滑动、三指上划）结束时，每次都会触发一次点击行为，导致视频播放暂停。触摸板不受此问题影响。

## 根因分析

### 背景：两层输入架构

GestureSign 使用两条独立的输入路径，在同一 UI 线程上串行执行：

1. **WM_POINTER 路径**：`PointerInputTargetWindow` 通过 `RegisterPointerInputTarget` 拦截所有触摸屏的 pointer 消息，决定注入（`InjectTouchInput`）还是阻止
2. **WM_INPUT 路径**：`MessageWindow` 通过 RawInput 获取 HID 原始数据，经 `PointEventTranslator` → `PointCapture` 进行手势识别

`WM_POINTER` 消息**先于** `WM_INPUT` 消息到达，因此 `PointerInputTargetWindow` 在 `PointCapture` 做手势判断之前就已经完成了注入/阻止决策。

### 问题根因

当 `BlockTouchInputThreshold=2` 时，`PointerInputTargetWindow` 根据当前帧的手指数量决定是否注入：

```
shouldInject = touchInfos.Length < _blockTouchInputThreshold
```

时序如下：
1. 第一根手指 DOWN → `touchInfos.Length=1 < threshold=2` → `shouldInject=true` → **DOWN 被注入到应用**
2. 第二根手指 DOWN → `touchInfos.Length=2 >= threshold=2` → `shouldInject=false` → **BLOCKED**
3. 第一根手指被标记为 BLOCKED，后续 UPDATE/UP 不注入

**结果**：应用收到第一根手指的孤立 DOWN（无对应 UP/CANCEL），Windows 在触摸序列异常结束时合成触摸结束事件（不带 CANCELED），浏览器将其解释为 tap → click。

根本原因是第一根手指到达时无法预知后续会有更多手指，注入决策仅基于当前帧手指数。

## 解决方案：延迟注入 + 移动距离阈值

在 `PointerInputTargetWindow` 中实现延迟注入机制，与 `PointCapture` 的 `multiFingerDelay` 逻辑对齐：

### 核心逻辑

当第一根手指 DOWN 到达时，**不立即注入**，而是缓存该事件。根据后续情况决定注入还是阻止：

1. **延迟超时**（`AppConfig.MultiFingerDelay`，默认 50ms）：无更多手指到达 → 判断为单指操作 → 注入缓存的 DOWN + 累积的 UPDATE
2. **移动距离超过阈值**（`AppConfig.TapDistanceThreshold / 2`，默认 20px）：用户在拖动 → 注入缓存的 DOWN + 累积的 UPDATE
3. **更多手指到达**（`touchInfos.Length >= threshold`）：多指手势 → 不注入缓存的 DOWN，直接 BLOCK 所有

### 仅处理第一根手指

延迟逻辑只在 `_pointerIdList.Count == 0`（无已跟踪手指）时生效。后续手指到达时正常走现有的 BLOCK 逻辑。

### 修改文件

- `GestureSign.Daemon/Filtration/PointerInputTargetWindow.cs`

### 关键实现

- `ShouldDelayInjection()`：判断是否需要延迟（第一根手指 DOWN + threshold>=2 + delay>0）
- `StartPendingInjection()`：缓存 DOWN 事件，记录位置，启动 `System.Windows.Forms.Timer`
- `FlushPendingInjection()`：注入缓存的 DOWN + 累积的 UPDATE
- `CancelPendingInjection()`：多指到达时取消缓存，标记手指为 BLOCKED
- `ProcessPointerMessage()` 中集成延迟期间的移动距离检测和 UP 事件处理
