# 微信窗口激活后卡死问题复盘

## 1. 问题现象

在手势执行 `ActivateApp` 切换微信（`Weixin.exe`）后，窗口偶发出现“假死”：

- 点击无响应，输入失效
- 新消息不刷新或刷新明显延迟
- 关闭按钮有 hover 态，但实际命中异常
- 任务栏图标可见，进程未退出，但窗口交互失效

同类现象在部分 Chromium/Qt/MFC 应用也可见（如企业微信、通达信），但微信路径最敏感。

## 2. 根因演进

### 2.1 第一层根因：`AttachThreadInput` 破坏输入队列一致性

历史实现中，`ForceSetForegroundWindow` 通过 `AttachThreadInput` 合并 GestureSign 与目标窗口线程输入队列后再激活。

该方式在多进程/多线程 UI 应用（Chromium/Qt）上风险高：

1. 合并输入队列后焦点、捕获、按键状态被共享
2. Detach 时状态未必能在复杂消息泵下完整恢复
3. 可能导致窗口继续显示但不再消费输入消息

因此第一轮修复已移除 `AttachThreadInput`、`SetFocus` 等路径。

### 2.2 第二层问题：窗口状态恢复职责分散，导致重复恢复与状态漂移

在后续修复中，出现过两类回归：

1. **双重 `SW_RESTORE`**：调用方先恢复，底层激活再恢复，造成 `Maximized -> Normal` 降级
2. **隐藏窗口/最小化窗口处理分散**：不同插件各自 show/restore，时序与语义不一致

这也是“卡死概率下降但偶发仍在、且窗口状态偶尔异常”的主要来源。

### 2.3 误判澄清：窗口大小重置并非“异步最小化”本身导致

复盘后确认，窗口大小重置的关键在于**恢复语义与恢复次数**，不是“最小化同步/异步”这个单变量。

结论：

- 不需要为了统一风格把最小化全部改成异步
- 优先保证恢复链路语义单一、时序可控

## 3. 最终设计原则（当前版本）

### 3.1 语义分层

- `SystemWindow.ForegroundWindow = ...`
  - 保持“纯前台切换”语义
  - 不承担 show/restore 副作用
- `SystemWindow.TryActivateWindow(...)`
  - 承担“完整激活语义”
  - 显式参数控制副作用：
    - `showHidden`
    - `restoreMinimized`

### 3.2 副作用显式化

由调用方按场景声明是否允许副作用：

- `ActivateApp` / `NextApplication`：`showHidden: true, restoreMinimized: true`
- 其他仅需前台切换的路径：继续使用 `ForegroundWindow` 纯语义

避免“全局一刀切自动 show hidden”带来的跨模块副作用。

## 4. 关键实现变更

### 4.1 `ManagedWinapi/Windows/SystemWindow.cs`

新增：`TryActivateWindow(IntPtr hWnd, bool showHidden = false, bool restoreMinimized = true)`

关键点：

1. `hWnd == IntPtr.Zero` 直接返回 `false`
2. `showHidden` 时：
   - `ShowWindowAsync(SW_SHOW)`
   - 轮询 `IsWindowVisible` 最多 `5 x 10ms`（50ms）
3. `restoreMinimized` 时：
   - `ShowWindowAsync(SW_RESTORE)`
   - 轮询 `IsIconic` 最多 `5 x 10ms`（50ms）
4. 前台短路判断放到副作用处理之后
   - 解决“已在前台但仍最小化/隐藏”时被提前返回的问题
5. `ForceSetForegroundWindow` 保持纯前台切换，不再承担 show/restore
6. 继续移除侵入式兜底：不再使用 `SetWindowPos(..., SWP_SHOWWINDOW)`

### 4.2 `GestureSign.CorePlugins/ActivateApp/ActivateAppPlugin.cs`

- 单窗口与多窗口路径统一改为调用 `TryActivateWindow(...)`
- 删除调用方散落的 `ShowWindow(SW_SHOW)` / `RestoreWindow()` 逻辑
- 保留最小化 toggle 行为（`MinimizeIfActivated`）

### 4.3 `GestureSign.CorePlugins/NextApplication.cs`

- 切换与最小化恢复统一调用 `TryActivateWindow(...)`
- 删除遗留的 `ShowWindow(SW_RESTORE)` 路径
- 清理未使用的 `SetForegroundWindow` P/Invoke 声明

### 4.4 `GestureSign.CorePlugins/MaximizeRestore.cs`

- 保持使用 `ShowWindowAsync(SW_MAXIMIZE/SW_RESTORE)`
- 避免跨进程同步 `ShowWindow` 的阻塞放大

## 5. 为什么这样更稳

1. **职责收敛**：激活副作用统一在一个入口，调用方不再各写各的
2. **时序可控**：对 show/restore 增加短等待，降低“未完成状态切换就前台激活”的竞态
3. **副作用可审计**：参数显式传递，review 时可直接判断调用点是否应 show/restore
4. **兼顾兼容性**：`ForegroundWindow` 仍可用于“只切前台”的低副作用场景

## 6. 验证结果（截至 2026-02-28）

- `dotnet build GestureSign.sln -c Debug` 通过
- `uiAccessRelease` 构建仅有既有打包目录权限 warning（非本次逻辑引入）
- 关键行为验证通过：
  - 隐藏窗口激活不再因竞态偶发失败
  - 前台窗口处于最小化/隐藏态时可正确恢复
  - `NextApplication` 与 `ActivateApp` 调用链语义一致

## 7. 风险与边界

- `TryActivateWindow` 当前最大等待时间为约 100ms（showHidden 50ms + restore 50ms）
  - 这是为降低竞态所做的有界等待，需在“响应性 vs 稳定性”间平衡
- 极少数应用若消息泵异常拥塞，仍可能超过等待窗口
  - 此时应优先补日志，不建议回退到侵入式 `SetWindowPos(..., SWP_SHOWWINDOW)`

## 9. 托盘恢复场景的进一步尝试（2026-03）

微信通过 Ctrl+W 隐藏到托盘后，SafeMode（纯 SetForegroundWindow）和 AttachThreadInput 模式均会导致窗口卡死（关闭按钮高亮但整个窗口不响应输入）。

### 9.1 尝试过的方案及结论

| 方案 | 结果 |
| ---- | ---- |
| `ShowWindow(SW_RESTORE)` 同步恢复 | 窗口显示但卡死 |
| `PostMessage(WM_SYSCOMMAND, SC_RESTORE)` 异步恢复 | 与 ShowWindow 无区别，仍卡死 |
| `PostMessage(WM_NCMOUSELEAVE)` 尝试重置 hover 状态 | 无效 |
| `SendMessage(WM_ACTIVATE, WA_ACTIVE)` 尝试模拟激活 | 无效 |
| 移除 `mouse_event` 零位移鼠标注入 | 对微信无影响（但影响其他应用，见下文） |

### 9.2 根因分析

Qt 应用（微信基于 Qt 5.15）的窗口隐藏/显示由内部状态机管理。通过托盘图标点击触发的恢复会经过 Qt 的完整恢复管线（包括输入队列重新关联、内部焦点状态同步等），而外部 Win32 API（ShowWindow/PostMessage）只改变了 Win32 层面的可见性，无法触发 Qt 内部状态恢复，导致窗口可见但输入管线断裂。

### 9.3 结论

**已确认为 Qt 框架已知限制**，外部 Win32 API 无法正确恢复 Qt 托盘应用的内部状态。在代码中以注释形式记录此限制。

用户点击卡死窗口的标题栏按钮（最小化/最大化）可恢复正常——这验证了问题在于 Qt 内部状态而非 Win32 窗口状态。

## 10. 关键信息给 Reviewer

此次调整不是”继续堆补丁”，而是一次语义收敛：

- 把”切前台”与”完整激活（可带副作用）”拆成两个明确 API
- 把隐藏/最小化的恢复策略从调用方散点逻辑收敛为可配置、可复用、可审计的统一路径

这也是后续继续稳定窗口激活链路的基础。
